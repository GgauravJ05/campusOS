# Database normalization — a worked case study

DBMS Unit 3 (Normal Forms) asks for a decomposition to 1NF/2NF/3NF/BCNF on a
real relation. This document walks that process on CampusOS's own schema,
one violation at a time, as each is fixed — rather than inventing a textbook
example, this project has genuine ones.

Status legend: ✅ fixed | ⬜ not yet fixed. See `docs/SYLLABUS-MAPPING.md` for
where this fits among the other DBMS syllabus rows.

## Violation 1 — `venues.equipment TEXT[]` breaks 1NF ✅ fixed

**The rule.** First Normal Form requires every attribute to hold a single,
atomic value. A repeating group — several values crammed into one column —
is not atomic, no matter how the database happens to store it.

**The violation, as it stood.**

```sql
CREATE TABLE venues (
    ...
    equipment TEXT[] NOT NULL DEFAULT '{}'   -- e.g. {PROJECTOR,MIC,AC}
);
```

One venue's row held a whole list of equipment items in one cell. This looks
convenient (`equipment @> ARRAY['PROJECTOR']` reads nicely) but it breaks
every reason 1NF exists:

- **No referential integrity on the values.** `'PROJECTOR'` and `'PROYECTOR'`
  (a typo) are both just strings inside an array; nothing stops the second
  from being inserted, and nothing links either one to a canonical list.
- **No independent row to attach facts to.** There is no way to add "this
  projector needs a bulb replacement" without a shape change.
- **Awkward, non-standard queries.** Searching "venues with every one of
  these three items" needed the non-relational `@>` (array-contains)
  operator instead of an ordinary join.

**The fix — decompose into a lookup table and a junction table.**

```sql
CREATE TABLE equipment (
    equipment_id    INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    equipment_code  VARCHAR(40) NOT NULL UNIQUE
);

CREATE TABLE venue_equipment (
    venue_id        INTEGER NOT NULL REFERENCES venues(venue_id)    ON DELETE CASCADE,
    equipment_id    INTEGER NOT NULL REFERENCES equipment(equipment_id) ON DELETE CASCADE,
    PRIMARY KEY (venue_id, equipment_id)
);
```

`equipment` is now a real entity with its own identity and a uniqueness
constraint the database enforces (no more typo duplicates). `venue_equipment`
records the many-to-many fact "this venue has this equipment" — one row per
fact, each attribute atomic. Every value in every column is now a single,
indivisible item: 1NF.

**This is also the project's composite-primary-key example** (DBMS Unit 3,
"keys"). `venue_equipment` has no surrogate `id` column at all. The pair
`(venue_id, equipment_id)` *is* the identity of the fact being recorded —
there is no meaningful way for the same pair to appear twice, and no reason
to invent an id that would just duplicate what the pair already says. This
was previously a real gap: every other junction table in the schema
(`club_members`, `event_registrations`) uses a surrogate PK plus a separate
`UNIQUE` constraint on the pair, which works but isn't the textbook case.

**What changed for the application.** `venue.service.js` still returns
`equipment: ["AC", "PROJECTOR", ...]` in every API response — normalizing
storage is not a reason to break every client that reads the venue shape.
The array is now assembled per request with

```sql
LEFT JOIN LATERAL (
  SELECT array_agg(eq.equipment_code ORDER BY eq.equipment_code) AS equipment
    FROM venue_equipment vex JOIN equipment eq ON eq.equipment_id = vex.equipment_id
   WHERE vex.venue_id = v.venue_id
) ve ON TRUE
```

and the equipment filter (`GET /api/venues?equipment=...`) became one
`EXISTS` subquery per requested code, ANDed together, instead of the
non-standard `@>` operator — an ordinary semi-join per required item.

**Where to see it:**

```sql
\d venue_equipment          -- composite primary key, both foreign keys
SELECT * FROM equipment ORDER BY equipment_code;
```

`tests/integration/venues.flow.test.js` exercises the full read/write path,
including "replaces a venue's equipment with no other field changing" for the
write side.

## Violation 2 — `events.eligible_departments` / `eligible_years` arrays ✅ fixed

Same 1NF shape as violation 1, on `events`: two repeating-group columns,
`eligible_departments INTEGER[]` and `eligible_years SMALLINT[]`.

**The fix — two separate junction tables, not one.**

```sql
CREATE TABLE event_eligible_departments (
    event_id      INTEGER NOT NULL REFERENCES events(event_id)      ON DELETE CASCADE,
    department_id INTEGER NOT NULL REFERENCES departments(department_id) ON DELETE CASCADE,
    PRIMARY KEY (event_id, department_id)
);

CREATE TABLE event_eligible_years (
    event_id      INTEGER  NOT NULL REFERENCES events(event_id) ON DELETE CASCADE,
    academic_year SMALLINT NOT NULL CHECK (academic_year BETWEEN 1 AND 5),
    PRIMARY KEY (event_id, academic_year)
);
```

Two independent multi-valued facts about one entity — "which departments"
and "which years" — get **separate** junction tables, never one combined
`(event_id, department_id, academic_year)` table. An event open to IT and
CS, for years 2 and 3, means "IT or CS" **and** "year 2 or 3" — four
eligible combinations, not two rows to pick from. Combining them into one
table forces a choice between storing every combination (a cartesian
product no one asked for) or an arbitrary subset (silently dropping some of
the intended combinations) — that mixing of two independent facts into one
relation is itself a 4NF violation. See `CLAUDE.md`'s database rules for
this exact point, and `venue_equipment` above for a case where one junction
table *is* correct (equipment is the venue's only multi-valued fact here).

Two more composite primary keys, same reasoning as `venue_equipment`: the
pair (or `event_id` + `academic_year`) already identifies the fact, so no
surrogate id is needed.

**What changed for the application.** `event.service.js`'s `EVENT_SELECT`
now assembles `eligible_departments`/`eligible_years` per request with two
`LEFT JOIN LATERAL` + `array_agg` subqueries, so every existing API response
and the in-memory eligibility check in `eligibility.js` are unchanged — they
still see plain JS arrays. Publishing and editing an event replace the
junction rows through a `syncEligibility()` helper (delete-and-reinsert,
same pattern as `venue.service.js`'s `syncEquipment`).
`dashboard.service.js`'s "events I could still register for" query, which
used to test `cardinality(...) = 0 OR x = ANY(...)` against the arrays, is
now two `NOT EXISTS (...) OR EXISTS (...)` pairs against the junction
tables — the same "empty means open to everyone" rule, expressed as
ordinary joins instead of an array function.

**Where to see it:**

```sql
\d event_eligible_departments   -- composite primary key
\d event_eligible_years         -- composite primary key
```

`tests/integration/events.flow.test.js`, `publish.concurrency.test.js` and
`governance.flow.test.js` (the student dashboard's "open events" count)
exercise the full read/write path unchanged.

## Violation 3 — `venues.location` is derivable, not a 3NF violation ⬜ not yet fixed

`venues.location` mostly duplicates `'Floor ' || floor || ', ' || building`
(a handful of shared spaces store a free-text override instead, e.g. "Behind
Main Building"). Storing a value that can be computed from other columns in
the same row is not a classic 3NF violation — normal forms are defined
*within* one relation, and this is one column depending on two others in
that same relation, which 3NF does not forbid. The precise term is an
**update anomaly from stored derivable data**: change `floor` or `building`
and `location` can silently go stale. Planned fix: compute it in the
application layer (or a generated column) for the common case, keeping room
for the free-text override the shared spaces need.

## Violation 4 — `events.booked_seats` is a stored aggregate ⬜ not yet fixed

`booked_seats` duplicates `COUNT(*) FROM event_registrations WHERE event_id
= ... AND status <> 'CANCELLED'`. It exists for a real reason — FR15's seat
race needs a single row to take `SELECT ... FOR UPDATE` on, and counting
child rows under that lock is equally correct but slower under load — so
this is a deliberate, documented denormalization for concurrency, not an
oversight. `chk_events_booked_within_capacity` is the database's backstop
against it ever drifting past `max_seats`. Recorded here so the mapping is
honest about which "3NF violations" are bugs and which are traded-off
on purpose.
