Problem Statement & Motivation

The problem at MMCOE
1

Double-booked rooms

Paper / WhatsApp requests let one venue go to two clubs

2

Slow, unrecorded approvals

Days to approve; no record of who decided

3

Missed events

Notices scattered across chat groups & forms

4

No usage insight

Faculty lack venue, club and attendance reports

Motivation

  • Team members faced double-booked halls and late notices
  • Simultaneous approvals are a real concurrency problem: needs transactions, locks, constraints
  • Syllabus PBL topic: event management with registration, attendance, notifications, analytics
  • Faculty need an uneditable decision record

Objectives & Scope

Key objectives

  1. Online venue request with approve / reject (mandatory reason)
  2. Zero double bookings under concurrent load (row lock + exclusion constraint)
  3. Event feed, seat reservation within capacity, waitlist & recommendations
  4. Reminders 48 h and 2 h before events
  5. JWT + RBAC across 5 roles; append-only audit trail
  6. PDF / CSV reports; apply 2nd-year IT subjects

In scope

Venue directory, clash + buffer checking, multi-tier approvals, clubs, event publishing, RSVP + waitlist, notifications, dashboards, audit log, reports

Out of scope

Payments / ticketing, calendar integration, chat, RFID / biometric attendance, native apps, ERP / LMS integration, AI recommendations, public hosting

Literature Survey & Research Gap

#Paper / SourceApproachLimitation
1Ajith et al., Campus Venue Booking System, 2025 [1]Firebase app: availability check, alternative slots, faculty priorityClaims 99% of clashes prevented; test method not given
2Rodiyah et al., classroom reservation, Esa Unggul Univ., 2025 [2]CodeIgniter + MySQL; admin approval; gray-box testingSimultaneous requests not tested
3Antony et al., EduNexus facility booking, 2026 [3]Node, Express, MongoDB; roles, calendar, approve / rejectNo concurrency testing reported in the abstract
4Hermawan and Suharso, billiard table booking, 2025 [4]Firebase transactions; 2 to 11 users: double booking 100% to 0%Fixed slots; no approval step or buffer time
5Sandhu et al. [5]; Eswaran et al. [6]Role-based access models; locking and phantom rowsFoundation for our 5-role RBAC and venue row lock

Research gap

The campus systems we read check availability and add approvals, but none tests two approvals arriving at the same instant. Papers that do test concurrency use fixed slots with no approval chain or buffer. CampusOS adds a venue row lock, a DB exclusion constraint, multi-tier approval, a 15-min buffer and an audit trail, checked by 20-way race tests.

Methodology

  • Incremental phases: DB → API → tests → UI
  • Critical rules enforced in code and in the database
  • Unit, integration, concurrency, schema, UI-flow tests
  • GitHub monorepo, CI on every push, dated change log

Two independent safety layers

Layer 1
Transaction + SELECT … FOR UPDATE row lock
Layer 2
PostgreSQL EXCLUDE constraint, capacity trigger, append-only audit trigger
Result
Rules hold even if application code has a bug

Conclusion & Future Scope

Conclusion

  • One role-based platform replaces scattered manual venue and event handling
  • Double booking and overbooking prevented by locks + DB constraints
  • 20 of 21 FRs complete, FR1 partly (college users only); 1,278 tests pass
  • 2nd-year IT concepts applied in real features

Future scope
